# dotmet-repair-loop

## 目的
dotmet の解析結果を使い、修正、検証、再解析を繰り返してコードベースの状態を収束させる。
報告やレビューだけが目的のときは、修正せず状態を残す。

## 判断の原則
解析を通すために設計契約を弱めない。
`findings` をなくすための変更が設計目標を変える場合は、候補と影響を整理してから進める。
rules 変更で `findings` が減った場合は、コード改善、対象範囲の正当な変更、検出力の低下を分ける。

## フロー

### Phase 1: 入力固定
作業目的と入力を固定する。

- 解析確認、状態改善、構成更新、結果整理のどれを目的にするか。
- 対象の解析単位、target set、rules の指定があるか。
- 変更範囲がコード、rules、target set、実行環境のどれか。
- `findings` を解消する作業か、分類して状態を整理する作業か。

作業目的は次で扱う。

| 状態 | 扱い |
| --- | --- |
| 作業目的が明示されない。 | 状態改善として扱う。 |
| 報告、レビュー、CI 結果整理だけが目的として明示されている。 | 結果整理として扱う。 |
| 解析対象または修正範囲が不明で、作業範囲を越える可能性がある。 | 確認してから進める。 |

合意が必要な設計変更を、確認なしに rules や target set へ反映しない。

### Phase 2: 解析診断
`$dotmet-analysis` で解析し、診断分類を受け取る。

分類の優先順位と信頼範囲は `$dotmet-analysis` の診断結果に従う。

### Phase 3: 継続判断
解析診断を受けて、このフローで続けるか、完了または中断として状態を残すかを決める。

継続、完了、中断は次の順で判断する。

| 順序 | 状態 | 扱い |
| --- | --- | --- |
| 1 | 診断分類が `decision-required` である、または設計目標、改善対象、依存許可、しきい値、解析対象の意味を変える必要がある。 | 確認事項を残して中断する。 |
| 2 | 現在の作業範囲を越える変更が必要である。 | 必要な対応を残して中断する。 |
| 3 | 手元で検証できない、同じ原因の修正と再解析が失敗済み、または検出力を下げる変更しか残っていない。 | 直前の状態、残った原因、確認事項を残して中断する。 |
| 4 | 診断分類が `dotmet-issue` である。 | 再現条件、入力、レポート、実行した解析を残して完了する。 |
| 5 | 診断分類が `report-only` である、または結果確認として開始し、修正まで求められていない。 | 診断、影響、必要な対応を残して完了する。 |
| 6 | 状態改善または作業後の確認として扱っており、修正対象を一つ選べる。 | Phase 4 へ進む。 |
| 7 | 修正対象を決められない。 | 確認事項を残して中断する。 |

継続する場合は Phase 4 へ進む。
完了または中断する場合は、Phase 9 へ進む。

### Phase 4: 修正対象の選択
Phase 3 で継続すると決めた場合だけ、原因に対応する修正対象を一つだけ選ぶ。
原因が複数ある場合は、主原因を一つ選んで処理し、再解析で次の状態を判断する。
ここでは修正領域だけを選ぶ。
rules、target set、コード設計の詳細判断は、修正領域を選んだ後に扱う。

| 診断分類 | 修正領域 | 扱い |
| --- | --- | --- |
| `code-change-needed` | コード修正 | コードを rules に合わせて修正する。 |
| `rules-update-needed` | rules 更新 | `$dotmet-rules` の判断結果を使う。 |
| `target-update-needed` | target set 更新 | `$dotmet-targets` の判断結果を使う。 |
| `configuration-or-environment` | 構成または実行環境 | 入力、復元、参照解決、実行環境を修正する。 |

### Phase 5: 修正
選んだ対象だけを修正する。
コード、rules、target set、実行環境を同時に変更しない。

rules または target set を変更する場合は、該当スキルで確定した差分だけを適用する。
差分が設計契約や解析対象の意味を変える場合は、修正せず Phase 3 に戻す。
環境修正でコード構造や設計契約を変えない。
dotmet 側の失敗が疑われる場合は、コードや rules を回避的に変更しない。
`findings` を減らすためだけに、改善対象を外したり、依存許可を広げたり、分類を粗くしたりしない。

### Phase 6: 検証
コードを修正した場合は、変更範囲に対応する検証を実行する。
rules または target set を更新した場合は、設定が解析入力として成立するか確認する。
実行環境を修正した場合は、同じ入力で解析を開始できるか確認する。

### Phase 7: 再解析
検証後は、同じ目的と入力で再解析する。
入力を変える場合は、変更した理由を結果に残す。

再解析で診断分類が残る場合は、Phase 3 に戻る。
再解析で修正対象が残っていない場合は、Phase 8 へ進む。

### Phase 8: 停止判断
同じ入力で再解析し、残った問題の扱いが決まり、現在の作業範囲で選べる修正領域が残っていない状態になったら止める。

- 解析不能状態が残っていない。
- 解析対象の解決が目的に対して成立している。
- rules ファイルを指定または検出した場合は `rules validate` のレポートが成立している。rules がない場合は、`rulesCoverage = notConfigured` と組み込みしきい値の利用が目的に合っている。
- rules の適用状態が目的に合っている。
- `findings` が修正済み、既存負債、対象外、確認事項に分類されている。
- `findings` の減少が rules の検出力低下によるものではない。

停止条件を満たし、現在の作業範囲で対応が残っていない場合は、完了として Phase 9 へ進む。
残る対応が rules または target set の検出力を弱める変更だけである場合は、中断として Phase 9 へ進む。
同じ原因で再失敗している場合は、中断として Phase 9 へ進む。
停止条件を満たさない場合は、Phase 3 に戻る。

### Phase 9: 作業状態を残す
最後に次を短くまとめる。

- 実行した解析と入力。
- 採用した診断分類。
- 行った修正。
- 実行した検証。
- 再解析結果。
- 残った `findings`、構成不整合、確認事項。
- 最終状態（完了または中断）と、その根拠。
