# dotmet-targets

## 目的
**target set** は、dotmet が一つの解析単位として扱う対象群の定義である。
dotmet が解析する単位を決め、target set ファイルに入れる構成を判断する。
target set は解析入力を決めるものであり、rules の分類や依存方針を決めるものではない。

## フロー

### Phase 1: 解析候補を出す
解析候補を調べ、解析単位として扱える対象を出す。

候補は、採用候補、除外候補、確認が必要な候補に分ける。
候補を外す場合は、解析目的との関係で理由を残す。
目的が曖昧な場合は、候補と確認事項を残す。

この Phase では、リポジトリのアーキテクチャ方針を決めない。

### Phase 2: 解析単位を決める
解析目的に照らして、target set が必要か、単一対象の指定で足りるかを決める。

target set が必要な場合は、次のいずれかに当たる。

- 複数の解析対象を一つの dotmet 実行で扱いたい。
- `adapter` が異なる対象を同じ解析単位で扱いたい。
- 複数候補があり、暗黙選択では解析単位が曖昧になる。
- 解析対象の組み合わせを固定したい。

単一対象で足りる場合は、次のいずれかに当たる。

- 主要な解析候補が一つだけある。
- 特定の解析対象だけが指定されている。
- 複数候補があっても、同時解析ではなく個別解析のほうが目的に合う。

確認事項が残る場合も、根拠に基づく仮判断を置けるなら解析単位を仮に固定する。
確認事項が残ることを、target set の未成立として扱わない。

### Phase 3: target set を作成、更新、レビューする
作成または更新では、最初に [target set JSON 契約](references/target-set-contract.md) を読み、必須構造と値の制約を固定する。
そのうえで、子ターゲット、`adapter`、パス、`id` を決めて JSON を書く。
レビューでは、JSON を直接書き換えず、妥当な点、問題点、必要な差分案を分ける。

#### 子ターゲット
子ターゲットは、解析結果を分けて読む必要がある境界で分ける。
同じ解析単位に含めるほうが目的に合う構成は分けない。
主対象から外れる構成単位は、解析目的に必要な場合だけ子ターゲットにする。

#### `adapter` とパス
- `adapter` は解析対象の実体に合う値を書く。
- ソリューションファイルを指す場合は `solutionPath` を使う。
- プロジェクトファイルまたはプロジェクトルートを指す場合は `projectPath` を使う。
- パスとプロパティの機械制約は [target set JSON 契約](references/target-set-contract.md) に従う。
- `adapter` を自動検出させたいという理由だけで、target set 内の `adapter` を省略しない。

#### `id`
- target set の `id` はプロダクト、リポジトリ、または解析対象群を表す安定名にする。
- 子ターゲットの `id` は短く、役割や成果物が分かる名前にする。
- `id` の機械制約は [target set JSON 契約](references/target-set-contract.md) に従う。
- 短期的な都合やパスだけに依存する名前は避ける。
- 既存 `id` は、解析履歴や比較の意味が変わるため、理由なしに変更しない。

#### 配置と出力
target set の標準配置は `.dotmet/targets.json` とする。
別配置の target set を扱う場合は、指定されたパスを使う。

JSON を作成したら、含めた対象と外した対象の理由を残す。

#### レビュー
- 宣言されたパスが現在のリポジトリに存在するか。
- `adapter` とパス種別が一致しているか。
- 主要な解析対象が漏れていないか。
- target set に入っていない候補を外す理由が残っているか。
- 既存 `id` の変更が必要な変更か。

### Phase 4: 検証する
作成または更新では、target set が dotmet の解析入力として解決できるか確認する。
レビューでは、完了条件に達しない状態を評価結果として扱う。
[target set JSON 契約](references/target-set-contract.md) の検証方法を使い、構文検証だけで終えない。

次を確認する。

- [target set JSON 契約](references/target-set-contract.md) に適合している。
- 各子ターゲットの `adapter` とパス種別が一致している。
- 宣言されたパスがリポジトリ内に存在する。
- dotmet の解析入力として解決できる。

target set を使って解析対象の漏れや解析失敗を隠さない。
target set の判断だけで解消できない問題は、target set の変更で回避しない。

### Phase 5: 作業状態を残す
target set の作成、更新、レビューは、次の状態まで進める。

| 状態 | 意味 |
| --- | --- |
| 完了 | 解析対象が固定され、target set が必要な場合は JSON として成立し、dotmet の解析入力として解決できる。 |
| 確認事項あり | 解析対象は仮に固定され、target set は成立しているが、解析目的や対象の含め方に確認事項が残っている。 |
| 未完了 | 解析対象を固定できない、target set が成立していない、または dotmet の解析入力として解決できない。 |

最後に、次の判断に必要な状態を残す。
同じ内容を複数の項目へ分散しない。

- target set が必要か、単一対象で足りるか。
- 採用した解析対象。
- target set に含めた対象。
- target set に含めなかった候補と理由。
- 採用した `adapter`、パス、`id`。
- 既存 `id` を変更した場合は、その理由。
- レビューの場合は、評価結果と必要な差分案。
- 検証結果。
- 確認事項が残る場合は、仮判断、根拠、変更候補、再確認する内容。
- 未完了の場合は、target set だけで解消できなかった原因。

修正まで求められていない場合は、必要な差分案を残す。
