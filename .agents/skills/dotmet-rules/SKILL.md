# dotmet-rules

## 目的
rules は dotmet が検査する設計契約である。
rules ファイルには、`findings` の主語にしてよい改善対象、分類軸、分類条件、依存ルール、`coverage`、しきい値を入れる。

`subjects.owned` は、rules を適用し、`findings` の主語にしてよいソースの境界である。
解析入力に含まれるソースと、rules を適用するソースは分けて扱う。

JSON を作成または変更する前に [rules JSON 契約](references/rules-contract.md) を読み、必須のルート構造、マッチ条件、依存ポリシーの評価規則を固定する。

## 作業原則
現在の構造は根拠であり、正しい設計として写す対象ではない。
rules には、設計契約として検査したい境界を入れる。

作成と更新では、`rulesCoverage = full` だけで完了しない。
`full` の後に設計契約レビューを行い、主語、分類、許可の検出力を確認する。

rules だけで直せる問題は、確認事項にせず、該当 Phase に戻って修正する。
確認事項として残せるのは、名称の確定、意図の確認、検出力を弱めない仮判断の確認だけである。

判断を確定できない項目でも、検出力を弱めない仮判断として rules に反映できる場合は反映する。
その場合は、決めるべきこと、今回 rules での扱い、その扱いの影響を分けて残す。

## 作業のフェーズ
作成、更新、レビューは同じ Phase で扱う。
違いは、rules を編集するか、評価結果だけを残すかである。

作成と更新では、`継続` を最終状態にしない。
`継続` は該当 Phase へ戻るための作業状態として扱う。
レビューでは、完了条件に達しない状態を評価結果として残してよい。

### Phase 1: 入力と作業種別を固定する
作業種別、rules のパス、対象コードベースの有無、編集可否を固定する。
rules の標準配置は `.dotmet/rules.json` とする。
別配置の rules を扱う場合は、指定されたパスを使う。
新規作成では [rules JSON 契約](references/rules-contract.md) のコマンドで dotmet のテンプレートを生成し、その構造から編集を始める。

| 作業種別 | 扱い |
| --- | --- |
| 作成 | 改善対象、分類軸、分類条件、依存ルール、`coverage` を作り、Phase 8 まで進める。 |
| 更新 | 既存 rules、現在の構造、設計契約を分けて見て、必要な差分だけ入れる。 |
| レビュー | rules を変更せず、Phase 8 まで評価し、問題、根拠、必要な差分案、確認事項を残す。 |

この Phase では、作業種別、rules のパス、対象コードベースの有無、編集可否を残す。

### Phase 2: 改善対象を固定する
この Phase では、`findings` の主語にできる範囲を決める。
分類軸や依存ルールはまだ決めない。

解析入力内のソースを、改善対象、依存ルール上の相手、解析上の根拠、解析対象外に分ける。

| 分類 | 扱い |
| --- | --- |
| 改善対象 | `subjects.owned` で定義する。ownership の漏れを独立した条件で検査する必要がある場合だけ `localSubjectsMustBeOwned` を使う。 |
| 依存ルール上の相手 | `subjects.owned` に入れず、必要な分類だけを与える。 |
| 解析上の根拠 | 依存解決や判断材料として使うが、rules の主語にしない。 |
| 対象外 | rules の対象にも依存ルール上の相手にも使わない。 |

改善対象にする根拠は、このプロジェクトで修正責任を持つ対象として説明できることである。
解析入力に含まれること、依存解決に使うこと、分類に必要なことは根拠にならない。

未分類を減らす目的で、改善対象の境界を広げない。
検出対象から外す目的で、改善対象のソースを `subjects.owned` から外さない。

解決済みの外部参照と unowned support は、`subjects.external` に列挙しなくても `subject: "external"` に一致できる。
`subjects.external` は外部の相手を明示的な matcher で補足する場合だけ使い、依存先の棚卸しには使わず、`subjects.owned` と重ならない範囲にする。

`localSubjectsMustBeOwned` は、ローカル `subject` のうち `subjects.owned` に含まれることを要求する範囲を、ownership とは独立した条件で指定する。
`subjects.owned` の代わりに改善対象を定義したり、同じ matcher を複製したりするためには使わない。
`ownedSubjectsMustClassify` は、`subjects.owned` の `subject` に必要な分類軸だけに使う。

この Phase では、`subjects.owned` に入れる範囲、入れない範囲、その理由を残す。
改善対象として仮判断を置ける場合は rules に反映し、確認事項として残す。

### Phase 3: 設計境界を集める
この Phase では、改善対象の中にある layer、domain、役割境界を集める。
現在の構造は根拠として使い、正しい設計としてそのまま写さない。

境界の根拠として、配置、名前、参照方向、公開単位、実行単位、生成元、編集対象、解析上の利用、既存の設計記述を見る。
単一の根拠だけで境界を確定しない。
名前空間、assembly、project、directory は境界の根拠であり、それだけで設計境界を探索したことにしない。

設計パターン、役割名、呼び出し方向、状態の所在、入出力の責務、公開契約から生じる役割境界も見る。
役割境界とは、同じ改善対象の中で分けるべき実装上の役割、依存方向、状態や入出力の責務である。

境界候補は次に分ける。

| 分類 | 扱い |
| --- | --- |
| 反映できる境界 | `subjects.owned`、分類軸、依存ルール、`coverage` に反映する。 |
| rules にあるが保護されていない境界 | 依存ルールまたは `coverage` の不足として扱う。 |
| 推定できる境界 | 複数の根拠が揃う場合は rules に反映し、残る不確実性を確認事項として残す。 |
| 確認が必要な境界 | 候補、根拠、影響、決めるべき点を残す。 |
| 改善対象外の境界 | `subjects.owned` に入れない理由を残す。 |

この Phase では、rules に反映する境界、確認事項として残す境界、改善対象外にする境界を残す。
反映できる境界を候補として残すだけで終えない。

### Phase 4: 分類軸と分類条件へ写す
この Phase では、Phase 3 で集めた境界を分類軸と分類条件へ写す。
依存許可は Phase 5 で決める。

分類軸は、設計契約に必要なものだけを定義する。
未分類を消すための広い受け皿分類を置かない。
分類軸を採用したら、その軸が何を検出するためのものかを決める。

| 軸 | 役割 |
| --- | --- |
| `layer` | 依存方向を表す。 |
| `domain` | 独立させる責務境界を表す。 |
| `codeKind` | 異なる分類系統の境界を表す。 |

分類条件は、分類軸が表す境界に合わせて選ぶ。
物理配置の条件と設計境界の条件を混同しない。

| 分類対象 | 判断 | 優先する条件 |
| --- | --- | --- |
| 改善対象 | 修正対象として扱えるソースか。 | `pathPrefix`、`projectExact`、`assemblyExact` |
| `layer` | 依存方向を持つ役割か。 | `namespacePrefix`、`namespaceExact`、`assemblyExact` |
| `domain` | 独立させる責務単位か。 | `namespacePrefix`、`assemblyExact`、`projectExact` |
| `codeKind` | `layer` や `domain` とは別の性質で分けるか。 | `namespacePrefix`、`pathSegment`、`tagExact`、`subjectKindExact` |
| `subjects.external` | 依存ルール上の相手として区別するか。 | `assemblyExact`、`namespacePrefix` |

`domain` は改善対象の責務境界を表す。
`subjects.external` の分類は、依存ルール上の相手として区別する範囲に限る。
改善対象の責務境界と依存先分類を同じ意味で混ぜない。

`pathPrefix` は、改善対象の範囲や物理配置を表す条件として使う。
`layer`、`domain`、役割境界を `pathPrefix` だけで分類しない。

名前空間、assembly、project、directory が食い違う場合は、どれを設計境界として採用するかを判断する。
設計境界として採用した根拠と、補助条件として使った根拠を分ける。

分類条件が粗く、禁止したい依存や責務越境を検出できない場合は、rules が成立していても完了にしない。

この Phase では、分類軸、分類条件、分類条件に使った根拠を残す。
各分類軸の検査目的を決め、設計境界を表す分類軸を Phase 5 の依存ルールで使える状態にする。

### Phase 5: 検査ルールを書く
この Phase では、分類済みの対象に対して依存ルールとしきい値を書く。
分類軸や改善対象の範囲はここで広げない。

依存ルールは、検出したい境界越境を検出できる粒度で書く。
現状依存が存在することを、許可する理由にしない。

| 粒度 | 使い方 |
| --- | --- |
| `domain` + `layer` | 両方の境界を守る。 |
| `domain` | `domain` 境界を守る。 |
| `layer` | `layer` 境界を守る。 |
| `codeKind` | `codeKind` 境界を守る。 |
| `subject: "owned"` | `subjects.owned` 全体で許可範囲を決める。 |

同一分類内だけを許可する場合も、別の設計境界がその中にあるなら、同値条件または明示許可で依存範囲を狭める。
許可範囲を広げる判断を置く場合は、検出対象から外れる境界越境を明示する。
現在の依存を許可するか、目標設計として禁止するかを確定できない場合は、許可範囲へ入れず確認事項として残す。

依存ルールを書いたら、許可グラフとして読む。
どの分類からどの分類へ依存できるかを確認し、検出したい越境が許可範囲に入っていないことを確認する。
`subject: "owned"` 全体への許可は、設計契約として説明できる場合だけ使う。
補助的な分類からの依存でも、依存してよい対象を説明できる範囲まで狭める。
`subject: "external"` を広く許可する場合は、改善対象のどの分類からどの外部分類へ依存してよいかを分ける。
外部依存を一括許可して改善対象内の境界や用途境界を検出できなくなる場合は Phase 5 に留まる。

次の許可は広い許可として扱い、狭められるか確認する。

- `subject: "owned"` を使う許可。
- `subject: "external"` を使う許可。
- 同一分類全体への許可。
- 補助的な分類から広く依存できる許可。

列挙した許可ごとに、守れる境界、検出できなくなる境界、狭められる条件を残す。
狭められる許可は狭めてから Phase 6 へ進む。

しきい値は、品質契約がある場合、または既存値を見直す場合だけ扱う。
新規 rules では、追加する根拠がある場合だけ定義する。
[rules JSON 契約](references/rules-contract.md) のしきい値規則に従い、組み込み標準を緩める値を採用しない。

この Phase では、依存ルール、許可範囲、検出対象にした境界越境、しきい値を扱った場合はその目的を残す。

### Phase 6: coverage を検証する
rules を作成または更新したら、[rules JSON 契約](references/rules-contract.md) に従って `rules validate` のレポートを確認する。
対象コードベースがある場合は、解析で rules が改善対象へ適用されているか確認する。

[rules JSON 契約](references/rules-contract.md) の意味に従って `rulesCoverage` を読み、`full` を設計契約レビューの通過とはみなさない。

この Phase では、`rules validate` の結果、`rulesCoverage` の状態、未解消項目と戻り先を残す。
`rulesCoverage = full` になったら完了せず、Phase 7 へ進む。

### Phase 7: 設計契約レビューを通す
この Phase では、`rulesCoverage = full` になった rules の検出力を見る。
作成と更新では、この Phase に失敗した rules を完了しない。

rules 作成の目的は `findings` を減らすことではない。
`findings` は、定義した境界が現在のコードに照らして何を検出するかを確認するために使う。

主語、分類、許可の三つを確認する。
各評価で、通過と判断した根拠を残す。
根拠には、対象の rules 定義、使われている分類軸、対応する依存ルールを含める。
根拠を残せない評価は通過扱いにしない。

| 観点 | 通過条件 |
| --- | --- |
| 主語 | `subjects.owned` が改善対象だけを含み、改善対象の漏れを `coverage` から外して隠しておらず、依存ルール上の相手を主語にしていない。 |
| 分類 | 各分類軸に検査目的があり、広い受け皿、異なる役割の混在、物理配置だけの境界、改善対象の責務境界と external 分類の混線がない。 |
| 許可 | 依存許可グラフを読んだとき、検出したい越境、同一分類内の別境界、用途を限定すべき external 依存が許可範囲に入っていない。 |

分類漏れの検出だけに使われている軸は、境界を保護していない。
未保護の境界を「次回詳細化」「土台」「確認事項」として残して完了してはならない。

この Phase では、主語、分類、許可の評価、問題がある場合の原因、必要な差分案を残す。

### Phase 8: 作業状態を残す
この Phase では、作業結果を次の判断に使える状態で残す。
rules の内容はここで新しく判断しない。
報告では Phase 名を使わない。
Phase 名は戻り先の判断にだけ使い、報告では改善対象、分類条件、依存許可、coverage、解析対象、コード修正のような作業領域で書く。

| 状態 | 意味 |
| --- | --- |
| 完了 | rules が成立し、対象コードベースがある場合は `rulesCoverage` が `full` で、設計契約レビューを通っている。 |
| 確認事項あり | rules が成立し、対象コードベースがある場合は `rulesCoverage` が `full` で、設計契約レビューを通し、検出力を弱めない確認だけが残っている。 |
| 継続 | rules の更新だけで解消できる未分類、曖昧な分類、未評価、未適用、分類条件、設計契約レビューの問題が残っている。該当 Phase に戻る。 |
| 未完了 | rules の更新だけでは完了条件に到達できない原因が残っている。 |

作成と更新では、完了、確認事項あり、未完了のどれかまで進めてから作業を区切る。
`継続` は戻り先の Phase で処理する。
未保護の境界、広すぎる許可、改善対象の混入、分類軸の未使用がある場合は `確認事項あり` にしない。
判断したこと、仮判断、確認が必要なことを分けられない場合は、完了または確認事項ありにしない。
レビューでは、完了条件に達しない状態を評価結果として扱う。

最後は次の見出しで返す。
該当がない見出しには、なしと書く。

#### 成果物
- `subjects.owned` の境界。
- `subjects.owned` に入れなかった範囲と理由。
- 採用した分類軸、分類条件、依存ルールの粒度。
- しきい値を追加または更新した場合は、その目的と影響。

#### 判断したこと
- 確定した判断。
- 仮判断として rules に入れたこと。
- rules に入れなかった候補と理由。

#### 確認が必要なこと
- 決めるべきこと。
- 今回 rules ではどう扱ったか。
- その扱いの影響。

#### 検出力
- rules で検出できる境界。
- rules で検出できない境界と理由。
- 検出される既存の境界越境。
- 確認事項が残る場合は、それが検出力を弱めない理由。

#### 検証結果
- 設計契約レビューの結果。
- `rules validate` の結果。
- `rulesCoverage` の状態。

#### 次の扱い
- レビューの場合は、問題、根拠、必要な差分案。
- `継続` または未完了の場合は、原因と見直す作業領域。

## 戻り先
作成または更新では、rules だけで直せる問題を確認事項にしない。
問題が出た場合は、原因に対応する Phase に戻る。
この表は作業の制御に使う。
報告では Phase 名ではなく作業領域を書く。

| 結果 | 戻る場所 | 報告で残す作業領域 |
| --- | --- | --- |
| 改善対象の混入、漏れ、または `findings` の主語として説明できない範囲がある。 | Phase 2 | 改善対象の見直し |
| 設計境界の探索不足、または反映できる境界が候補のまま残っている。 | Phase 3 | 設計境界の見直し |
| 分類軸の不足、分類条件の粗さ、分類軸の未使用、責務境界と依存先分類の混線がある。 | Phase 4 | 分類条件の見直し |
| 依存許可が広すぎる、検出したい越境が許可範囲に入っている、現状依存をそのまま許可している。 | Phase 5 | 依存許可の見直し |
| `rules validate`、`rulesCoverage`、未分類、曖昧な分類、未評価、未適用に問題がある。 | Phase 6 | coverage と検証の見直し |
| 設計契約レビューで主語、分類、許可のいずれかが通らない。 | Phase 2、Phase 3、Phase 4、Phase 5 の原因箇所 | 設計契約の見直し |
| 解析対象または target set の問題で rules を適用できない。 | `dotmet-targets` または `dotmet-analysis` | 解析対象の見直し |

## 報告後の再開
rules への指摘が返った場合は、その指摘を再開入力として扱う。
指摘内容から戻る場所を判断し、rules を修正する。
rules を変更した場合は、Phase 6 と Phase 7 を再実行する。

## 完了条件
作成と更新は、Phase 8 の `完了` または `確認事項あり` の条件を満たし、指定された見出しで判断根拠と検証結果を報告できるまで完了にしない。
レビューでは、完了条件に達していない点を問題、根拠、必要な差分案として残す。
