# dotmet-project-config

## 目的
dotmet の解析構成を、解析入力と設計契約が一致した状態へ整える。

target set は解析入力を決める。
rules は `findings` の主語にしてよい改善対象、分類軸、依存許可、`coverage` を決める。

## サブエージェント
構成依頼とレビュー依頼では、別々のサブエージェントを使う。

### 構成担当
構成担当は target set と rules を編集し、変更内容、判断したこと、確認が必要なこと、検証結果を返す。

- 渡すもの：対象コードベース、作業目的、編集可否、使用する skill。
- 渡さないもの：期待する rules の形、疑っている問題、修正方針。

### レビュー担当
レビュー担当は、作成または更新された rules を評価し、ファイルを変更しない。

- 渡すもの：作成済み rules、対象コードベース。
- 渡さないもの：期待する結論、疑っている問題、修正方針。

### 担当の維持
同じ構成担当と同じレビュー担当を維持する。
構成の更新と再修正は同じ構成担当に任せる。
rules の再レビューは同じレビュー担当に任せる。
既存の担当を継続できない場合は、新しい担当を固定して同じ依頼単位を引き継ぐ。
サブエージェント機能を使える環境では、構成担当とレビュー担当を必ず分ける。

サブエージェント機能が存在しない実行環境では、その制約を記録する。
その場合も、構成結果とレビュー結果を分けて扱う。

## フロー
解析対象と rules をまとめて整え、レビュー結果に応じて戻る場所を決める。
Phase 2 から Phase 7 は、完了条件を満たすまで繰り返す。

### Phase 1: 目的と入力を固定する
構成を作成するのか、更新するのか、レビューするのかを固定する。
目的がコード修正なのか解析構成なのかを分ける。

構成担当とレビュー担当を起動して固定する。
構成担当へ渡す対象コードベース、作業目的、編集可否を決める。
レビューだけを行う場合は、target set と rules を更新しない。
コード修正や `findings` 解消が主目的なら、`dotmet-repair-loop` を使う。

### Phase 2: 解析対象を固定する
構成担当へ、`$dotmet-targets` を使った解析入力の固定を依頼する。

target set では解析入力だけを決める。
改善対象の境界、分類軸、依存ルールは rules 側で決める。

### Phase 3: 改善対象の境界を固定する
構成担当へ、解析入力内のソースを、改善対象、依存先としての分類、解析上の利用に分けるよう依頼する。

解析入力に含まれるだけの範囲は、改善対象として扱わない。
rules を適用し、`findings` の主語にしてよいソースだけを `subjects.owned` に入れる。
依存先として区別したいだけの範囲は、`subjects.owned` に入れず、依存ルール上の相手として分類する。

### Phase 4: rules を整える
構成担当へ、固定した解析対象に対する `$dotmet-rules` の実行を依頼する。

Phase 2 の解析対象、Phase 3 の改善対象、作業目的、編集可否を渡す。
Phase 6 から戻った場合は、レビュー結果、必要な差分案、確認が必要なことを渡す。
構成担当から次を受け取る。

- 変更内容。
- 判断したこと。
- 確認が必要なこと。
- 検証結果。
- 見直す作業領域。

### Phase 5: 成立確認する
`$dotmet-analysis` を使い、解析対象の解決、`rules validate`、改善対象への rules 適用を確認する。

`rulesCoverage = full` だけで構成完了にしない。
`$dotmet-rules` の設計契約ゲートでは、通過したゲートと通過できなかったゲートを分ける。
成立確認では、成立している範囲、成立していない範囲、見直す作業領域を残す。

### Phase 6: rules をレビューする
rules を作成または更新したら、レビュー担当へ `$dotmet-rules` を使ったレビューを依頼する。
Phase 5 が成立していても、レビューを省略しない。

レビュー担当へ、作成済み rules と対象コードベースを渡す。
レビュー担当から次を受け取る。

- 問題。
- 根拠。
- 必要な差分案。
- 確認が必要なこと。
- 見直す作業領域。

### Phase 7: 戻る場所を決める
Phase 5 または Phase 6 の結果から、戻る場所を一つ決める。
同時に複数の戻り先を処理しない。

| 状態 | 戻る場所 |
| --- | --- |
| 解析対象、path、adapter、target set がずれている。 | Phase 2 |
| 改善対象の境界がずれている。 | Phase 3 |
| rules の分類軸、依存許可、`coverage`、設計契約レビューに問題がある。 | Phase 4 |
| レポートの読解、成立状態、原因分類だけを確認する必要がある。 | Phase 5 |
| rules レビューが未実施、または再レビューが必要である。 | Phase 6 |
| 構成が完了条件を満たしている、または修正まで求められていない。 | Phase 8 |
| `findings` のコード修正まで必要である。 | Phase 8 |

この表の Phase 名は作業制御にだけ使う。
報告では、解析対象、改善対象、分類条件、依存許可、coverage、レビュー、コード修正のような作業領域として書く。

Phase 4 へ戻った後は、Phase 5 の成立確認と Phase 6 のレビューを再実行する。
レビュー担当が差分案を返した場合は、その差分案を同じ構成担当へ渡す。
レビュー担当が問題なし、または検出力を弱めない確認事項だけを返す状態になるまで完了にしない。

コード修正へ移る場合は、Phase 8 で構成状態を残してから `dotmet-repair-loop` に移す。

`$dotmet-rules` が戻り先を返している場合は、その戻り先、原因、根拠、必要な差分案を保持する。
返された戻り先は、Phase 4 で構成担当へ渡す。
返された戻り先の意味をここで再定義しない。

### Phase 8: 構成状態を残す
固定した解析対象、改善対象、rules、成立確認、レビュー結果を分けて残す。
未完了の場合は、原因、戻り先、報告で残す作業領域を分けて残す。
同じ内容を複数の項目へ分散しない。

#### 構成の要約
- 固定した解析対象または target set。
- `subjects.owned` に入れた改善対象。
- 改善対象ではないが依存先として分類した範囲。
- rules に反映した分類軸、分類条件、依存ルール。

#### 判断の状態
- 確定した判断。
- 仮判断として target set または rules に入れたこと。
- 入れなかった候補と理由。

#### 確認が必要なこと
- 決めるべきこと。
- 今回の rules または target set ではどう扱ったか。
- その扱いの影響。

#### 検出力と検証
- 設計契約ゲートの通過結果。
- 保護できる境界と保護されていない境界。
- `rulesCoverage` の状態。
- 構成の検証結果。
- 確認事項が残る場合は、それが検出力を弱めない理由。

#### 次の扱い
- レビューの場合は、問題、根拠、必要な差分案。
- 未完了の場合は、原因と見直す作業領域。

## 完了条件
解析対象、改善対象の境界、rules が固定され、rules が改善対象へ適用されている状態で完了する。

対象コードベースがある場合は、次をすべて満たす。

- `rules validate` が `pass` である。
- `rulesCoverage = full` である。
- `$dotmet-rules` の設計契約ゲートを通過している。
- rules レビューが通過している、または検出力を弱めない確認事項だけが残っている。

rules の成立や `rulesCoverage` の充足が、検出したい境界を許可範囲へ入れた結果なら完了にしない。

未解消の構成不整合が残る場合は未完了として状態に残す。
検出力を弱めない判断だけが残る場合は確認事項として保持する。
レビューでは、完了条件に達しない状態を評価結果として扱う。
修正まで求められていない場合は、必要な差分案を残して区切る。

## 報告後の再開
構成結果への指摘が返った場合は、その指摘を再開入力として扱う。
指摘内容から戻る場所を判断し、必要な構成担当またはレビュー担当へ戻す。
rules を変更した場合は、成立確認とレビューを再実行する。
